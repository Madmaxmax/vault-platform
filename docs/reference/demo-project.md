# Тестовый проект для демонстрации функций HashiCorp Vault

В качестве демонстрационного проекта будет использоваться небольшая веб-платформа с архитектурой Frontend + Backend + Database. Приложение не хранит пароли, API-ключи и другие конфиденциальные данные в исходном коде или обычных конфигурационных файлах. Вместо этого оно получает необходимые секреты из Vault после успешной аутентификации. Проект должен продемонстрировать следующие возможности Vault:
1. Централизованное хранение секретов.
2. Аутентификация приложений через AppRole.
3. Управление правами доступа через ACL-политики.
4. Получение и обновление секретов через API.
5. Управление временем жизни токенов.
6. Разделение доступа между пользователями и сервисами.
7. Аудит операций с секретами.
8. Шифрование и защита конфиденциальных данных.
9. Динамическая выдача учётных данных.
10. Резервное копирование и восстановление хранилища.

Цель: разработать тестовую инфраструктуру, демонстрирующую практическое применение HashiCorp Vault для безопасного управления секретами в многокомпонентном приложении.
Задачи:
- Развернуть HashiCorp Vault на сервере.
- Настроить защищённое хранилище секретов.
- Организовать аутентификацию приложений через AppRole.
- Создать отдельные роли для различных субъектов системы.
- Настроить политики доступа к секретам.
- Реализовать получение секретов через HTTP API.
- Продемонстрировать автоматическое обновление Vault-токенов.
- Настроить журналирование действий пользователей и приложений.
- Реализовать сценарии отказа в доступе при недостаточных правах.
- Продемонстрировать резервное копирование и восстановление.

Архитектура системы
Frontend: React / Next.js
Backend: Python
База данных: PostgreSQL
Secrets Management: HashiCorp Vault

## Функциональные модули проекта

### Модуль хранения секретов
Основной модуль проекта — централизованное хранилище конфиденциальных данных. В нём будут храниться:
| Путь | Содержимое | Назначение |
|---|---|---|
| secret/data/app/database | Логин и пароль PostgreSQL | Подключение backend к базе данных |
| secret/data/app/api | API-ключи | Взаимодействие с внешними сервисами |
| secret/data/app/jwt | Ключ подписи JWT | Подписание пользовательских токенов |
| secret/data/app/redis | Пароль Redis | Подключение к кэшу |
| secret/data/ci-cd/deploy	Учётные данные развёртывания | Автоматизация деплоя |
| secret/data/admin/integrations | Ключи административных интеграций | Работа административных инструментов |

Секреты должны быть доступны только соответствующим субъектам системы.

### Модуль аутентификации приложений через AppRole
Этот модуль должен демонстрировать, как backend-приложение получает доступ к Vault без использования пользовательского root-токена.

Для backend необходимо создать AppRole:
| Role | app-backend |
| Role ID | <ROLE_ID> |
| Secret ID | <SECRET_ID> |
| Policy | app-read |

### Модуль разграничения доступа
Необходимо создать несколько субъектов с различными полномочиями.

| Субъект | Назначение | Права | Путь |
|---|---|---|---|
| Vault Administrator | Управление Vault | Административные | Системные API и настроенные движки |
| Developer	| Чтение секретов разработки | read | secret/data/app/* |
| Backend Application | Получение секретов приложения | read | secret/data/app/* |
| CI/CD Runner | Работа с секретами деплоя | read | secret/data/ci-cd/* |

Для каждого субъекта следует создать отдельную ACL-политику.

Пример политики backend-приложения:
```bash
path "secret/data/app/*" {
  capabilities = ["read"]
}
```

### Модуль получения секретов backend-приложением
Backend должен иметь отдельный сервис для взаимодействия с HashiCorp Vault. Для реализации серверной части предлагается использовать Python + FastAPI.
Взаимодействие с Vault будет осуществляться через HTTP API с использованием AppRole. Для упрощения работы с Vault можно использовать официальную Python-библиотеку hvac.
Рекомендуемая структура проекта:

│   ├── config/
│   │   └── vault_config.py
│   │
│   ├── services/

│   │   └── database_service.py
│   │
│   ├── middleware/
│   │   └── auth_middleware.py
│   │
│   ├── controllers/
│   │   └── secrets_controller.py
│   │
│   ├── schemas/
│   │   └── vault_schema.py
│   │
│   └── main.py
│
├── requirements.txt
├── Dockerfile
└── .env.example

Файл src/config/vault_config.py должен содержать настройки подключения к Vault и параметры аутентификации.
Функции vault_service.py:
- Подключение к Vault.
- Аутентификация через AppRole.
- Хранение Vault Token в памяти процесса.
- Получение секретов из KV Secrets Engine v2.
- Продление токена.
- Повторная аутентификация при необходимости.
- Обработка ошибок Vault.

Для демонстрации можно реализовать следующие API:
| Endpoint | Метод | Назначение |
|---|---|---|
| /api/vault/status | GET | Проверка доступности Vault |
| /api/vault/auth | POST | Демонстрация аутентификации через AppRole |
| /api/vault/secrets | GET | Получение списка разрешённых секретов или их метаданных |
| /api/vault/secrets/database | GET | Получение конфигурации БД для внутреннего использования |
| /api/vault/secrets/refresh | POST | Повторное получение актуальных данных |
| /api/vault/token/status | GET | Проверка состояния токена |

### Модуль динамических секретов
Для более полной демонстрации возможностей Vault рекомендуется реализовать динамическую выдачу учётных данных PostgreSQL.
Принцип работы:
1. Backend аутентифицируется в Vault.
2. Backend обращается к database/creds/app-role.
3. Vault подключается к PostgreSQL с административными учётными данными, которые хранятся внутри Vault.
4. Vault создаёт временного пользователя PostgreSQL.
5. Vault возвращает приложению логин, пароль и lease.
6. Backend подключается к базе данных.
7. По истечении срока действия lease учётные данные отзываются Vault.

Пример запроса:
```bash
$ vault read database/creds/app-role
```

### Модуль аудита операций
Необходимо подключить Audit Device, который будет регистрировать обращения к Vault.
Пример файлового аудита:
```bash
$ vault audit enable file file_path=/vault/logs/audit.log
```

Для Docker или отдельного сервера нужно предварительно создать каталог, обеспечить права записи пользователя Vault и настроить сохранение логов.
В журнале необходимо отслеживать:
- Время обращения.
- Тип операции.
- Путь API.
- Результат выполнения.
- Информацию об аутентификации и токене в пределах предусмотренной схемы аудита.

### Модуль резервного копирования
Для демонстрации защиты данных необходимо реализовать резервное копирование Integrated Storage (Raft).
Команда создания снимка:
```bash
$ vault operator raft snapshot save vault-backup.snap
```

Проверка содержимого снимка:
```bash
$ vault operator raft snapshot inspect vault-backup.snap
```

Восстановление из снимка:
```bash
$ vault operator raft snapshot restore vault-backup.snap
```

## Критерии готовности проекта
Проект считается успешно реализованным, если выполняются следующие условия:
- Vault разворачивается по инструкции или через Docker Compose.
- Хранилище сохраняет данные после перезапуска контейнера.
- Настроена аутентификация через AppRole.
- Backend самостоятельно получает Vault Token.
- Backend получает пароль PostgreSQL из Vault.
- В исходном коде приложения отсутствуют реальные пароли и ключи.
- Разные субъекты имеют разные политики доступа.
- Запрещённые запросы завершаются отказом в доступе.
- Реализовано обновление или повторное получение токена.
- Включено журналирование операций.
- Создаётся резервная копия Raft.
- Проверено восстановление данных.
