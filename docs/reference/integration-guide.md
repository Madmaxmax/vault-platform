# Интеграция HashiCorp Vault в прикладные системы

Порядок развёртывания, настройки доступа и подключения продуктов

Документ фиксирует общую схему использования Vault для нескольких продуктов: размещение сервера, доступ приложений и CI/CD, выдачу временных пользователей PostgreSQL, а также порядок проверки интеграции. Он предназначен для инженеров, которые будут подключать новые сервисы, и администраторов платформы.

Примеры команд содержат условные имена продуктов и ресурсов. Перед использованием необходимо задать фактические пути, роли, политики и параметры доступа.

# 1. Назначение и границы решения
Vault используется как единая точка управления секретами для нескольких независимых приложений. Каждому продукту выделяются собственные роли и пути доступа; параметры другого продукта не должны становиться доступны по умолчанию. В первую очередь рассматриваются сервисы, работающие на Linux в Docker Compose, и базы PostgreSQL.

Целевой сценарий: приложение получает учётные данные к БД не из репозитория и не из постоянной переменной окружения, а через Vault Agent. Agent аутентифицируется в Vault, получает данные и записывает их в tmpfs; приложение читает подготовленный файл. Для PostgreSQL Vault может создавать отдельного временного пользователя с заданными полномочиями и временем жизни.

## 1.1. Что входит в документ
- Размещение Vault на отдельной виртуальной машине в Yandex Cloud и ограничение сетевого доступа.

- Права разработчиков, приложений, AI-агентов, CI/CD и администраторов.

- Аутентификация AppRole, доставка начального SecretID и работа Vault Agent.

- Dynamic Roles и Static Roles для PostgreSQL, сроки жизни и отзыв доступа.

- Порядок подключения нового продукта и минимальный набор эксплуатационных проверок.

## 1.2. Параметры, требующие согласования
До внедрения необходимо согласовать имена продуктов, эксплуатационные значения TTL, способ выдачи SecretID, схему резервирования Vault и процедуру восстановления. Перечень параметров для согласования приведён в разделе 10.

# 2. Архитектура и последовательность взаимодействия
На схеме предусмотрены три независимых прикладных контура Linux / Docker Compose. В каждом контуре расположены Vault Agent, временное хранилище в RAM и приложение. Все три приложения подключаются к PostgreSQL. Отдельно показаны Git, CI/CD Runner, Vault, Database Secrets Engine и аудит.

## 2.1. Роли компонентов
| **Компонент**           | **Функция**                                                                           |
|-------------------------|---------------------------------------------------------------------------------------|
| HashiCorp Vault         | Аутентификация клиентов, применение ACL, выдача и отзыв секретов, ведение аудита.     |
| Vault Agent             | Вход через AppRole, получение и обновление секретов, рендеринг файлов.                |
| tmpfs                   | Хранение выданных значений в оперативной памяти в пределах контейнера/узла.           |
| Приложение              | Использует выданный логин и пароль для подключения к PostgreSQL.                      |
| Database Secrets Engine | Создаёт динамические учётные записи или ротирует статические пароли.                  |
| CI/CD Runner            | Деплой приложения и, при отдельно выделенных правах, получение секретов для pipeline. |
| Audit logs              | Запись событий обращения к Vault и административных операций.                         |

## 2.2. Как проходит запрос
1.  Оператор готовит для продукта отдельную политику и роль AppRole; разрешает доступ только к нужным путям и ролям БД.

2.  При запуске Vault Agent получает RoleID и SecretID, устанавливает TLS-соединение с Vault и проходит AppRole login.

3.  Agent получает секрет из KV либо запрашивает database/creds/\<роль\> и записывает результат в tmpfs-файл.

4.  Приложение читает файл и открывает подключение к PostgreSQL. Если используется динамическая роль, учётная запись создаётся Vault через Database Secrets Engine.

5.  Vault контролирует Lease. Agent должен обновлять данные до истечения срока; приложение должно уметь переподключаться при смене реквизитов.

6.  События работы с Vault фиксируются в audit device.

Важно: стрелка между Vault Agent и Vault на схеме означает защищённое соединение и аутентификацию; Lease относится к выданным секретам, а не к самому TLS-соединению. Запросы PostgreSQL проходят от приложения к БД напрямую.

# 3. Размещение Vault в Yandex Cloud
## 3.1. Базовая конфигурация
### Характер нагрузки и ориентиры HashiCorp
Количество запросов к Vault API измеряется в RPS. Чтение KV, вход через AppRole, обновление токена и создание пользователя PostgreSQL дают разную нагрузку. Следует учитывать не только средний RPS, но и одновременный запуск приложений, долю операций записи и пиковую активность. RAM зависит не только от частоты запросов, но и от объёма данных и внутреннего состояния Vault.

В документации HashiCorp для более крупных установок с Integrated Storage приведены следующие ориентиры:

| **Ресурс**               | **Small**              | **Large**                |
|--------------------------|------------------------|--------------------------|
| CPU                      | 2–4 ядра               | 4–8 ядер                 |
| RAM                      | 8–16 ГБ                | 32–64 ГБ                 |
| Производительность диска | от 3 000 IOPS, 75 МБ/с | от 10 000 IOPS, 250 МБ/с |

Эти значения не следует приравнивать к минимальным требованиям небольшого внедрения. Профили Test, Medium и Large ниже — предварительные варианты, подлежащие проверке нагрузочными испытаниями.

Источники: [HashiCorp — Raft Reference Architecture](https://developer.hashicorp.com/vault/tutorials/day-one-raft/raft-reference-architecture), [HashiCorp Validated Designs](https://developer.hashicorp.com/validated-designs/vault/installation-guide/vms/detailed-design).

В качестве основы выбрана отдельная ВМ на базе Marketplace-образа «HashiCorp Vault with Yandex KMS support» (Ubuntu 22.04 LTS). Vault работает под systemd; Yandex KMS применяется для Auto Unseal. Перед настройкой необходимо проверить версию Vault и реальные пути к его конфигурации и данным в выбранном образе.

| **Профиль** | **Цель**                 | **vCPU** | **RAM** | **Системный SSD** | **SSD под Raft** | **Проверочная нагрузка** |
|-------------|--------------------------|----------|---------|-------------------|------------------|--------------------------|
| Test        | Разработка, проверки     | 1–2      | 2 ГБ    | 20–30 ГБ          | 10 ГБ            | 1–10 RPS                 |
| Medium      | Начальный рабочий контур | 2        | 4 ГБ    | 30 ГБ             | 20 ГБ            | 10–100 RPS               |
| Large       | Более активные обращения | 4        | 8–16 ГБ | 30 ГБ             | 20–40 ГБ         | 100–500 RPS              |

Нагрузки в таблице — цели испытаний, а не подтверждённые пределы производительности. Итоговую конфигурацию выбирают после замеров задержек, CPU, RAM, дисковых IOPS и реального соотношения чтения, записи, login и генерации учётных записей.

Для варианта Test допустимо начать с 2 ГБ RAM при небольшой нагрузке. Medium (2 vCPU, 4 ГБ RAM) рассматривается как начальная конфигурация для умеренного количества обращений; при росте задержек или использования памяти её можно пересмотреть до 8 ГБ. Large (4 vCPU, 8–16 ГБ RAM) предусматривает более активное использование API и динамической выдачи секретов. Для Raft существенны дисковые IOPS и задержки; параметры выбранного SSD необходимо проверять по [документации Yandex Compute Cloud](https://yandex.cloud/ru/docs/compute/concepts/disk).

## 3.2. Обязательные ресурсы и ограничения
- Compute Cloud: ВМ, отдельный SSD под Raft при необходимости.

- VPC: приватная подсеть и внутренний DNS; сертификат TLS должен включать используемое DNS-имя.

- Yandex KMS: симметричный ключ и сервисный аккаунт с ролью kms.keys.encrypterDecrypter на конкретный ключ.

- Security Group: TCP/8200 только от клиентов Vault и административных узлов; TCP/22 только через VPN/bastion или из административной сети. TCP/8201 внешним клиентам одиночной установки не нужен.

- Для обращения к KMS/IAM из приватной сети должен существовать контролируемый исходящий маршрут, например NAT.

- Доступ к Vault API напрямую из интернета не предусматривается.

### Ресурсы Yandex Cloud
| **Ресурс**              | **Назначение**                                         |
|-------------------------|--------------------------------------------------------|
| Compute Cloud           | Виртуальная машина с Vault                             |
| Системный SSD           | Ubuntu и установленное ПО                              |
| Отдельный SSD           | Данные Raft при выбранной схеме размещения             |
| VPC и приватная подсеть | Доступ приложений и администраторов по внутренней сети |
| Группа безопасности     | Ограничение SSH и Vault API                            |
| Сервисный аккаунт       | Права виртуальной машины на Yandex KMS                 |
| Симметричный ключ KMS   | Auto Unseal после перезапуска                          |
| Внутреннее DNS-имя      | Постоянное имя Vault для клиентов                      |
| VPN или bastion         | Администрирование без публикации Vault в интернет      |

### Последовательность создания ВМ
1.  Выбрать облако и каталог Yandex Cloud.
2.  Создать VPC, приватную подсеть и контролируемый исходящий доступ к KMS/IAM (например, через NAT).
3.  В KMS создать симметричный ключ, например `vault-unseal`, и сохранить идентификатор.
4.  Создать сервисный аккаунт `vault-kms` и назначить роль `kms.keys.encrypterDecrypter` на нужный ключ.
5.  Открыть [образ HashiCorp Vault with Yandex KMS support](https://yandex.cloud/en/marketplace/products/yc/vault-yckms), выбрать **Run in console** и развернуть ВМ в подготовленной подсети.
6.  Указать профиль ресурсов, сервисный аккаунт, SSH-ключ администратора и отдельный SSD при необходимости.
7.  Задать внутренний DNS и подготовить TLS-сертификат с этим именем.
8.  Разрешить TCP/22 только административной сети или VPN/bastion, TCP/8200 — разрешённым клиентам Vault. Для одиночной установки не открывать TCP/8201 внешним клиентам.

Образ основан на Ubuntu 22.04 LTS и предусматривает Auto Unseal через Yandex KMS. Vault работает под `systemd`; устанавливать стандартный пакет поверх Marketplace-образа без необходимости не нужно. Фактические пути конфигурации и данных проверяются после установки.

Подключение к виртуальной машине по SSH из разрешённой административной сети:

```bash
ssh -i ~/.ssh/id_ed25519 <VM_USER>@<VM_PRIVATE_IP>
```

# 4. Модель доступа к секретам
Доступ предоставляется через Vault policies, закреплённые за субъектом и конкретным продуктом. Для каждого продукта рекомендуется отдельный префикс KV и отдельная роль Database Secrets Engine. Схема имён ниже — рекомендуемый шаблон, не существующая настройка.

> secret/data/products/\<product\>/...
>
> secret/data/ci-cd/\<product\>/...
>
> database/creds/\<product\>-readonly
>
> database/creds/\<product\>-readwrite

## 4.1. Матрица доступа и принципы разграничения прав
| **Субъект**            | **Базовый набор прав**                            | **Как применять при интеграции**                                                                       |
|------------------------|---------------------------------------------------|--------------------------------------------------------------------------------------------------------|
| DevOps / администратор | create, read, update, delete, sudo на \*          | Не использовать как постоянную роль по умолчанию; привилегии распределить по административным задачам. |
| Разработчик            | read на secret/data/app/\*                        | Предоставлять доступ только к разрешённым данным своего продукта, желательно отдельно от production.   |
| AI-агент               | read на secret/data/app/\*                        | Отдельная машинная идентичность, минимум доступных путей; не делить токен с приложением.               |
| Приложение             | read на secret/data/app/\*                        | Персональная policy приложения; при БД — read на нужную database/creds/role.                           |
| CI/CD Runner           | create, read, update на secret/data/ci-cd/\*      | Отдельная роль Runner с путями конкретного pipeline и без глобальных прав.                             |
| Сервис backup          | read, create, update на sys/storage/raft/snapshot | Специальная policy на допустимые snapshot API, проверенная по используемой версии Vault.               |

Общий путь secret/data/app/\* не обеспечивает изоляцию нескольких продуктов. Для исключения перекрёстного доступа необходимо выделять отдельные пути и политики для каждого продукта.

В таблице показаны базовые полномочия и требования к их ограничению. Доступ sudo на \* предоставляет широкие административные привилегии и не должен назначаться постоянным рабочим ролям. Права необходимо разграничивать по функциям, продуктам и средам.


## 4.2. Субъекты, способы аутентификации и области доступа

Для каждого продукта и среды создаётся собственная машинная идентичность. Роли Vault и политики ACL не объединяются между приложениями, CI/CD и административными операциями. Матрица ниже определяет точки входа и права; базовые полномочия шести субъектов приведены в предыдущей таблице.

| **Субъект**                   | **Аутентификация в Vault**                            | **Политика / допустимый путь**                                                            | **Практическое ограничение**                                    |
|-------------------------------|-------------------------------------------------------|-------------------------------------------------------------------------------------------|-----------------------------------------------------------------|
| DevOps / администратор        | Именная учётная запись через утверждённый auth method | Административные API по утверждённым policies; полный доступ только в аварийной процедуре | Не использовать общий root token для ежедневной работы          |
| Разработчик                   | Именная учётная запись                                | read: secret/data/app/\* или область своего продукта                                      | Отделить dev/test от production                                 |
| AI-агент                      | Отдельная машинная роль                               | read: secret/data/app/\* или специально выделенный путь                                   | Запретить совместное использование токенов                      |
| Приложение / Vault Agent      | AppRole с RoleID и SecretID                           | read: secret/data/products/\<product\>/\* и database/creds/\<role\>                       | Роль уникальна для продукта и среды                             |
| CI/CD Runner                  | Отдельный auth method / AppRole                       | create, read, update: secret/data/ci-cd/\*                                                | Нет доступа к боевым секретам приложения без отдельного решения |
| Сервис резервного копирования | Отдельная служебная идентичность                      | read, create, update: sys/storage/raft/snapshot                                           | Разрешить только необходимые действия snapshot API              |

Последовательность регистрации приложения в Vault:

1. Администратор создаёт policy на собственный путь приложения и требуемую роль БД.

2. Администратор создаёт AppRole и назначает ей эту policy, TTL токена и срок действия SecretID.

3. Доверенный процесс получает RoleID и доставляет SecretID приложению либо Vault Agent по выбранному защищённому каналу.

4. Vault Agent вызывает auth/approle/login и получает клиентский токен с назначенными ACL.

5. С этим токеном Agent выполняет разрешённые операции secret/data/... или database/creds/...; Vault проверяет policy при каждом запросе.

6. Токены и выданные динамические секреты обновляются либо выдаются заново по правилам TTL и Lease; события фиксируются в аудите.

## 4.3. Пример policy для приложения

```hcl
# KV v2: чтение данных выбранного продукта
path "secret/data/products/product-a/*" {
capabilities = ["read"]
}
# Только одна динамическая роль PostgreSQL
path "database/creds/product-a-readonly" {
capabilities = ["read"]
}
```

В KV v2 путь /data/ используется при обращении к API. Для листинга метаданных потребовалась бы отдельная политика на /metadata/; добавлять её без потребности не следует.

# 5. Подключение приложения через AppRole и Vault Agent
## 5.1. Создание AppRole
AppRole подходит для машинного входа сервисов. Для каждого приложения создаётся собственная роль; RoleID сам по себе не является достаточным фактором аутентификации. SecretID необходимо передать по доверенному каналу.

```bash
vault auth enable approle
vault policy write product-a-read product-a-read.hcl
vault write auth/approle/role/product-a \
token_policies="product-a-read" \
token_ttl="1h" \
token_max_ttl="4h" \
secret_id_ttl="24h" \
secret_id_num_uses=1
vault read auth/approle/role/product-a/role-id
vault write -f auth/approle/role/product-a/secret-id
```

Значения 1h / 4h / 24h и одно использование SecretID приведены как параметры настройки AppRole. Перед внедрением нужно проверить, может ли Agent повторно войти после рестарта: одноразовый SecretID не подходит без механизма повторной выдачи или безопасного bootstrap.

## 5.2. Первичная доставка SecretID
Для первичной передачи SecretID могут использоваться переменные окружения, защищённый файл, Docker Secrets, Kubernetes Secret, response wrapping или доверенная внешняя система управления секретами. Для Docker Compose предпочтителен защищённый файл или механизм Docker Secrets с ограничением доступа. Response wrapping подходит, когда уже есть канал доставки одноразового wrapping token.

RoleID и SecretID нельзя добавлять в Git, Docker image или логи pipeline. Bootstrap-операция, перевыпуск SecretID, отзыв при компрометации и ответственный владелец должны быть описаны для каждого продукта.

Способы первичной доставки SecretID:``

| **Способ**                           | **Принцип передачи**                                   |
|--------------------------------------|--------------------------------------------------------|
| Переменные окружения                 | SecretID предоставляется при запуске приложения        |
| Защищённый файл                      | SecretID хранится в файле с ограничением прав          |
| Docker Secrets                       | Передача через механизм Docker                         |
| Kubernetes Secret                    | Передача SecretID в Pod через объект Kubernetes Secret |
| Response Wrapping                    | Получатель раскрывает одноразовый wrapping token       |
| Внешняя система управления секретами | Передача через доверенную инфраструктуру               |

## 5.3. Доставка секрета приложению
Agent запускается рядом с приложением, получает реквизиты и формирует файл в tmpfs. Приложение должно читать файл только после первого успешного рендеринга и корректно реагировать на последующие изменения. Само по себе обновление файла не означает, что уже открытые соединения PostgreSQL используют новый пароль.

Рекомендуется предусмотреть: готовность приложения только после появления файла; ограничение прав чтения; механизм обновления пула соединений; очистку временных файлов при остановке; отсутствие значений секретов в логах.

# 6. Выдача учётных данных PostgreSQL
## 6.1. Dynamic Roles и Static Roles
| **Способ**   | **Назначение**                                                   | **Управление доступом**                                     |
|--------------|------------------------------------------------------------------|-------------------------------------------------------------|
| Dynamic Role | Vault создаёт новую учётную запись на каждый запрос credentials. | SQL-шаблоны создания, продления и отзыва; Lease с TTL.      |
| Static Role  | Vault управляет паролем заранее существующего пользователя.      | Периодическая ротация пароля; имя пользователя сохраняется. |

Для продуктовых подключений, где допустима смена учётных записей, основным вариантом являются Dynamic Roles. Статические роли выбирают, когда приложение или сторонняя интеграция требует фиксированного имени пользователя.

## 6.2. Подключение Vault к PostgreSQL

Перед регистрацией динамических или статических ролей необходимо создать Database Config. Vault подключается к PostgreSQL по отдельной служебной учётной записи. В отличие от временных пользователей, она должна иметь право создавать роли, назначать подготовленные групповые роли и отзывать доступ. Для подключения выбирается имя сервиса PostgreSQL, доступное из сети Vault, и проверяется TLS.

Параметры подключения:

| **Параметр**                  | **Назначение**                                                                 |
|-------------------------------|--------------------------------------------------------------------------------|
| POSTGRES_HOST / POSTGRES_PORT | DNS-имя сервера PostgreSQL и порт (обычно 5432)                                |
| POSTGRES_DB                   | Целевая база, например app_db                                                  |
| VAULT_DB_USER                 | Служебный логин Vault для управления ролями                                    |
| VAULT_DB_PASSWORD             | Пароль служебной учётной записи; не записывать в репозиторий или историю shell |
| sslmode=verify-full           | Проверка сертификата сервера PostgreSQL; CA должен быть доверен Vault          |
| allowed_roles                 | Перечень ролей Vault, которым разрешено использовать данный Database Config    |

На стороне PostgreSQL администратор создаёт служебную роль и группирующую роль приложения. Конкретные права служебной роли зависят от версии PostgreSQL и принятой модели администрирования; приведённый вариант необходимо проверить на тестовом экземпляре.

```sql
-- выполняется администратором PostgreSQL
CREATE ROLE vault_db_admin LOGIN CREATEROLE PASSWORD '<secure-password>';
CREATE ROLE app_readonly NOLOGIN;
GRANT CONNECT ON DATABASE app_db TO app_readonly;
-- в базе app_db:
GRANT USAGE ON SCHEMA public TO app_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_readonly;
-- право назначать app_readonly новым пользователям
GRANT app_readonly TO vault_db_admin WITH ADMIN OPTION;
```

Команды регистрации Database Secrets Engine выполняются администратором Vault. В примере используются условные имена и значения. Пароль вводится через защищённый механизм доставки; передача его прямо в командной строке может привести к записи в историю или журналы.

```bash
vault secrets enable database
vault write database/config/postgres \
plugin_name="postgresql-database-plugin" \
allowed_roles="app-readonly,app-readwrite" \
connection_url="postgresql://{{username}}:{{password}}@postgres.internal:5432/app_db?sslmode=verify-full" \
username="vault_db_admin" \
password="<secure-password>"
vault read database/config/postgres
```

Если используется доверенный CA, необходимо обеспечить его доступность для процесса Vault и проверить параметры TLS в драйвере PostgreSQL. При записи connection_url плейсхолдеры {{username}} и {{password}} оставляются без подстановки: Vault заменяет их данными служебной учётной записи. Название db_name="postgres" в последующих командах соответствует имени config «postgres».

Проверка соединения проводится выдачей учётных данных после создания динамической роли и подключением под выданным пользователем. Наличие записи Database Config без успешного получения credentials не доказывает работоспособность интеграции.

## 6.3. SQL-шаблон динамического пользователя

Права временных пользователей лучше выдавать через заранее созданную группирующую роль PostgreSQL, например app_readonly. Шаблон выдаёт доступ к ней только на период действия динамического пользователя.

```sql
CREATE ROLE "{{name}}" WITH LOGIN
PASSWORD '{{password}}'
VALID UNTIL '{{expiration}}';
GRANT app_readonly TO "{{name}}";
```

Также допускается непосредственное назначение прав с помощью GRANT CONNECT, USAGE и SELECT. Такой способ подходит для узкого сценария, но для нескольких продуктов удобнее обслуживать набор привилегий через отдельные групповые роли. Права на новые таблицы следует настраивать отдельно — GRANT на существующие таблицы их не охватывает.

### Вариант с прямым назначением прав PostgreSQL
При прямом назначении прав разрешения выдаются на базу данных, схему и таблицы:

    CREATE ROLE "{{name}}"
    WITH LOGIN
    PASSWORD '{{password}}'
    VALID UNTIL '{{expiration}}';

    GRANT CONNECT ON DATABASE app_db TO "{{name}}";
    GRANT USAGE ON SCHEMA public TO "{{name}}";
    GRANT SELECT ON ALL TABLES IN SCHEMA public TO "{{name}}";

При использовании этого варианта следует отдельно проверить права на таблицы, созданные после выдачи разрешений, и ограничения для иных схем.

## 6.4. Создание, продление и отзыв

```sql
-- renew_statements
ALTER ROLE "{{name}}" VALID UNTIL '{{expiration}}';
-- revocation_statements
REVOKE app_readonly FROM "{{name}}";
DROP ROLE IF EXISTS "{{name}}";
```

При удалении пользователя PostgreSQL возможны ошибки, если у него остались активные соединения, объекты либо права. Прежде чем применять шаблон в рабочей среде, необходимо испытать отзыв на реальном сценарии работы пула соединений и обеспечить корректное освобождение сессий.

### Переменные SQL-шаблонов
| **Переменная**   | **Значение**                                      |
|------------------|---------------------------------------------------|
| `{{name}}`       | Имя временного пользователя, сформированное Vault |
| `{{password}}`   | Сгенерированный пароль                            |
| `{{expiration}}` | Время окончания действия реквизитов               |

## 6.5. Регистрация динамических ролей

```bash
vault write database/roles/product-a-readonly \
db_name="postgres" \
creation_statements=@readonly.sql \
renew_statements=@renew.sql \
revocation_statements=@revoke.sql \
default_ttl="1h" \
max_ttl="8h"
vault read database/creds/product-a-readonly
vault lease renew <lease_id>
vault lease revoke <lease_id>
```

default_ttl, max_ttl, lease_duration и lease_renewable определяют время жизни и возможность продления. В примере начальная выдача — на 1 час, максимально — до 8 часов при разрешённом продлении. При истечении Lease Vault инициирует отзыв; это не заменяет проверку завершения существующих PostgreSQL-сессий.

### Роль с правами чтения и записи
Для доступа с правами чтения и записи используется отдельная динамическая роль с более коротким TTL:``

    vault write database/roles/app-readwrite \
        db_name="postgres" \
        creation_statements=@readwrite.sql \
        revocation_statements=@revoke-readwrite.sql \
        default_ttl="30m" \
        max_ttl="4h"

После `vault read database/creds/app-readonly` Vault возвращает `username`, `password`, `lease_id`, `lease_duration` и `lease_renewable`. Значения `default_ttl` и `max_ttl` задаются при регистрации роли; продление разрешено только в рамках установленного предела.

## 6.6. Статическая роль

```bash
vault write database/static-roles/product-a-monitoring \
db_name="postgres" \
username="monitoring" \
rotation_period="24h"
vault read database/static-creds/product-a-monitoring
```

Пользователь monitoring должен существовать до настройки роли. Ротацию следует согласовать с временем обновления файла Vault Agent и переподключением приложения. Параметры Database Config, включая учётную запись, которой Vault создаёт и удаляет пользователей, задаются отдельно.

### Параметры статической роли и компоненты Database Secrets Engine
Статическая роль использует `username`, `rotation_period` и при необходимости `rotation_statements`. Первое значение задаёт существующего пользователя PostgreSQL, второе — период смены пароля, третье — выполняемые при ротации SQL-операции. В отличие от Dynamic Roles, имя пользователя сохраняется.

| **Компонент или параметр** | **Назначение**                             |
|----------------------------|--------------------------------------------|
| Database Config            | Подключение Vault к PostgreSQL             |
| Dynamic Roles              | Создание временных пользователей           |
| Static Roles               | Ротация паролей существующих пользователей |
| `creation_statements`      | SQL для создания пользователя              |
| `renew_statements`         | SQL для продления срока действия           |
| `revocation_statements`    | SQL для отзыва и удаления                  |
| `default_ttl`              | Начальный срок действия                    |
| `max_ttl`                  | Максимально допустимый срок                |
| `rotation_period`          | Период смены пароля статической роли       |

# 7. Подключение CI/CD и новых продуктов
## 7.1. Разделение задач CI/CD
Runner отвечает за сборку и деплой. Если pipeline нужен доступ к секретам, ему создают собственную policy и способ аутентификации; использовать AppRole продукта для CI/CD не следует. У runner не должно быть доступа ко всем секретам приложений только потому, что он выполняет деплой.

## 7.2. Порядок подключения продукта
1.  Зафиксировать продукт, среду (dev/test/prod), владельца, адрес сервера, имя БД и требуемые SQL-права.

2.  Выделить имена путей KV, AppRole, policies и database roles, исключив пересечения с другими продуктами.

3.  Проверить сетевой маршрут от Agent до Vault и от приложения до PostgreSQL; выдать доверенный CA для проверки TLS.

4.  Создать ограниченную policy, AppRole и механизм доставки начального SecretID.

5.  Подготовить Database Config и SQL-шаблоны, испытать выдачу и отзыв пользователя на тестовой БД.

6.  Подключить Agent, tmpfs и чтение файла в приложении; проверить запуск, обновление секрета и переподключение.

7.  Настроить аудит, мониторинг, инструкцию на случай недоступности Vault и процедуру ротации/отзыва.

8.  Только после испытаний повторить настройки в production, исключив перенос тестовых секретов.

## 7.3. Что хранить в репозитории
Допустимы шаблоны policies, конфигурации Vault Agent без секретов, SQL-шаблоны, Compose-файлы и инструкции запуска. Запрещено хранить действующие SecretID, токены Vault, ключи KMS и выданные пароли PostgreSQL.

# 8. Контроль работоспособности, аудит и сопровождение
## 8.1. Базовые проверки
- Vault доступен по внутреннему адресу, TLS-сертификат действителен и проверяется клиентом.

- Проходят AppRole login и выдача секрета для конкретной роли, но отсутствует доступ к путям другого продукта.

- Agent создаёт и обновляет файл; приложение не печатает секреты в stdout/stderr.

- Временный пользователь PostgreSQL может выполнять только разрешённые SQL-операции.

- Истечение TTL, ручной revoke, рестарт Agent и потеря доступности Vault не приводят к неконтролируемому использованию старых credentials.

- Audit device зарегистрирован, его события сохраняются в защищённом хранилище и доступны для разбора инцидентов.

## 8.2. Наблюдаемые показатели
При эксплуатации отслеживать успешность и задержки запросов Vault API, ошибки аутентификации, количество активных Lease, загрузку CPU/RAM, задержки и IOPS диска, доступность KMS, состояние службы и свободное место. Для приложений отдельно контролировать ошибки подключения к PostgreSQL после смены credentials.

## 8.3. Резервное копирование
Для создания снимков Raft используется отдельный сервис с ограниченным доступом к sys/storage/raft/snapshot. Реализация должна включать периодические снимки, защищённое хранение, проверку восстановления на отдельном стенде и контроль доступности ключа KMS. Наличие snapshot само по себе не доказывает возможность восстановления.

# 9. План внедрения и критерии приёмки
| **Этап**                      | **Результат**                                                                     |
|-------------------------------|-----------------------------------------------------------------------------------|
| 1\. Подготовка инфраструктуры | ВМ, частная сеть, DNS, TLS, KMS, диски и доступ администраторов.                  |
| 2\. Базовая настройка Vault   | Выполнена первичная настройка, доступ и аудит, согласована модель резервирования. |
| 3\. Контрольный продукт       | Созданы policy, AppRole, Agent, tmpfs; подтверждена выдача секрета.               |
| 4\. PostgreSQL                | Проверены создание пользователя, ограничение прав, renew и revoke.                |
| 5\. CI/CD                     | Runner деплоит продукт, не получая лишних полномочий.                             |
| 6\. Масштабирование           | Подключены следующие продукты по тому же порядку, без пересечений доступа.        |

Интеграция считается принятой, когда можно повторить развёртывание по инструкции, проследить происхождение каждого полномочия, проверить обновление/отзыв реквизитов и восстановить работоспособность после штатного перезапуска компонентов.
