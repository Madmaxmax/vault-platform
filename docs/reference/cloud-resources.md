# Развёртывание HashiCorp Vault в Yandex Cloud: требования и подготовка ВМ

## 1. Требования к ресурсам

### 1.1. От чего зависит нагрузка на Vault

Основной показатель для оценки нагрузки — **RPS (requests per second)**, то есть количество запросов к Vault API за секунду. При этом важно учитывать не только частоту запросов, но и то, какие именно операции выполняются.

Например, чтение секрета из KV, вход через AppRole, обновление токена и создание временной учётной записи PostgreSQL по-разному нагружают сервер. Чтение обычно дешевле операций, при которых Vault изменяет данные в хранилище. Пиковая нагрузка тоже имеет значение: при одновременном запуске приложений количество запросов может резко вырасти, даже если в обычном режиме обращения редкие.

В [рекомендациях HashiCorp по Vault с Integrated Storage](https://developer.hashicorp.com/vault/tutorials/day-one-raft/raft-reference-architecture) выбор CPU и дисковой подсистемы связывается с характером запросов и их интенсивностью. Потребление оперативной памяти в большей степени зависит от объёма данных и состояния, которые Vault держит в памяти. Поэтому привязывать RAM только к RPS некорректно.

Для сравнения в [HashiCorp Validated Designs](https://developer.hashicorp.com/validated-designs/vault/installation-guide/vms/detailed-design) указаны следующие ориентиры:

| Ресурс | Small | Large |
|---|---:|---:|
| CPU | 2–4 ядра | 4–8 ядер |
| RAM | 8–16 ГБ | 32–64 ГБ |
| Производительность диска | от 3 000 IOPS, 75 МБ/с | от 10 000 IOPS, 250 МБ/с |

Это конфигурации из документации HashiCorp для более широких сценариев эксплуатации. Для отдельного Vault с ограниченным объёмом данных целесообразно рассмотреть меньшие ресурсы и проверить их на предполагаемой нагрузке.

### 1.2. Варианты конфигурации

Для предварительного подбора ресурсов предлагаются три варианта. Значения RPS в таблице показывают **нагрузку, которую следует воспроизвести при испытаниях**, а не измеренную производительность каждой конфигурации.

| Параметр | Test | Medium | Large |
|---|---:|---:|---:|
| Использование | Разработка и проверка работы | Рабочая среда с умеренным числом обращений | Более интенсивная работа с Vault API |
| Нагрузка для проверки | 1–10 RPS | 10–100 RPS | 100–500 RPS |
| CPU | 1–2 vCPU | 2 vCPU | 4 vCPU |
| RAM | 2 ГБ | 4 ГБ | 8–16 ГБ |
| Системный диск | 20–30 ГБ SSD | 30 ГБ SSD | 30 ГБ SSD |
| Диск для данных Raft | 10 ГБ SSD | 20 ГБ SSD | 20–40 ГБ SSD |

**Test** подойдёт для знакомства с Vault, проверки аутентификации, политик и выдачи секретов. Для такого стенда достаточно начать с 2 ГБ RAM, если не планируется серьёзная нагрузка.

**Medium** — основной вариант для первоначального рабочего развёртывания: **2 vCPU и 4 ГБ RAM**. Он рассчитан на умеренное использование KV, аутентификации и других стандартных возможностей Vault. Если мониторинг покажет рост потребления памяти или задержек, конфигурацию можно увеличить до 8 ГБ RAM либо пересмотреть параметры диска.

**Large** стоит выбирать, когда обращения к API происходят часто, одновременно работает много клиентов или активно используются динамические секреты и ротация. В качестве отправной точки подходят **4 vCPU и 8 ГБ RAM**; необходимость увеличения до 16 ГБ определяется замерами.

Для Vault с Raft важно смотреть не только на свободное место, но и на **IOPS и задержки диска**. В Yandex Cloud эти показатели зависят от типа и размера диска. Перед заказом ВМ их следует сверить с [характеристиками дисков Compute Cloud](https://yandex.cloud/ru/docs/compute/concepts/disk).

## 2. Подготовка виртуальной машины в Yandex Cloud

### 2.1. Операционная система и способ установки

Для установки используется образ [HashiCorp Vault with Yandex KMS support](https://yandex.cloud/en/marketplace/products/yc/vault-yckms) из Yandex Cloud Marketplace. Образ основан на **Ubuntu 22.04 LTS** и содержит Vault с поддержкой автоматического снятия блокировки хранилища через Yandex Key Management Service (Auto Unseal).

Vault работает как служба `systemd`. Отдельно устанавливать стандартный пакет поверх Marketplace-образа не требуется. После создания ВМ необходимо проверить версию Vault и фактические пути к файлам конфигурации и данным: они зависят от используемой версии образа.

### 2.2. Какие ресурсы потребуются

| Ресурс Yandex Cloud | Для чего используется |
|---|---|
| Compute Cloud | Виртуальная машина с Vault |
| Системный SSD | Ubuntu и установленное ПО |
| SSD для данных | Хранение данных Vault (Raft), если используется отдельный диск |
| VPC и приватная подсеть | Доступ приложений и администраторов к Vault по внутренней сети |
| Группа безопасности | Ограничение доступа к SSH и Vault API |
| Сервисный аккаунт | Предоставление ВМ доступа к Yandex KMS |
| Симметричный ключ KMS | Auto Unseal после перезапуска Vault |
| Внутреннее DNS-имя | Постоянный адрес Vault для клиентов |
| VPN или bastion | Администрирование ВМ без открытия Vault в интернет |

### 2.3. Создание ресурсов

1. В консоли Yandex Cloud выбрать облако и каталог, в которых будет размещён Vault.
2. Создать VPC и приватную подсеть. Для работы с KMS и IAM предусмотреть исходящий доступ к необходимым сервисам Yandex Cloud, например через настроенный NAT.
3. В **Key Management Service** создать симметричный ключ, например `vault-unseal`. Сохранить его идентификатор — он понадобится при настройке Vault.
4. Создать сервисный аккаунт `vault-kms` и назначить ему роль `kms.keys.encrypterDecrypter` в области выбранного ключа.
5. Перейти к [образу Vault в Marketplace](https://yandex.cloud/en/marketplace/products/yc/vault-yckms), выбрать **Run in console** и создать ВМ в подготовленной подсети.
6. При создании ВМ выбрать подходящий профиль ресурсов, привязать сервисный аккаунт `vault-kms`, указать SSH-ключ администратора и при необходимости добавить отдельный SSD для данных.
7. Настроить внутреннее DNS-имя, по которому приложения будут обращаться к Vault. При дальнейшем включении TLS это имя должно присутствовать в сертификате.
8. Настроить группу безопасности: доступ по **TCP/22** разрешить только из административной сети или через VPN/bastion, по **TCP/8200** — только клиентам Vault и администраторам. Порт **TCP/8201** для внешних клиентов одиночной установки открывать не требуется.

Публиковать API Vault напрямую в интернете не рекомендуется. Для доступа сотрудников и администраторов лучше использовать приватную сеть и контролируемый канал подключения.

### 2.4. Проверка после создания ВМ

Подключиться к виртуальной машине по SSH:

```bash
ssh -i ~/.ssh/id_ed25519 <VM_USER>@<VM_PRIVATE_IP>
```

Проверить ОС, установленную версию Vault, службу и подключённые диски:

```bash
cat /etc/os-release
vault version
sudo systemctl status vault --no-pager
sudo systemctl cat vault
sudo ls -l /etc/vault.d/
lsblk -f
```
